# ADR-002: Enforce authorization in the database with RLS and permission-checked RPC functions

Formalizes PA1 **AD-02** · Based on ADR-00x proposed in PA3-C (Trần Gia Huy) · Date: 2026-11-17 · Deciders: Team T08 · Related: FR-04, FR-16, FR-19, BR-02, BR-03, NFR-03, AC-08, R04

| ADR | ADR-002: Enforce authorization in the database with RLS and permission-checked RPC functions |
|---|---|
| Status | accepted |
| Context | The Web App calls the Supabase Data API directly (ADR-001), so anyone with a valid login token can send requests without using our screens. Hiding a menu in React protects nothing. Crew leaders need **partial** access: some rows (only stages assigned to them) and some columns (they may change a stage's status but not its name; they may record attendance but must not see wage rates or phone numbers). An unrelated user must see nothing (NFR-03). |
| Decision | Enable Row Level Security on **every** table, with owner and active-member policies built on four `SECURITY DEFINER` helpers in a non-exposed schema (`private.is_project_owner`, `private.is_active_member`, `private.has_permission`, `private.is_assigned_stage`). Column-restricted actions go through `SECURITY DEFINER` RPC functions that check the permission themselves and touch only the allowed columns: `upsert_attendance`, `update_stage_progress`, `confirm_stage_plan`, `reorder_stages`, `accept_invitation`, `get_ai_project_context`. Crew leaders read worker names through the restricted views `worker_roster` and `attendance_sheet`, which have no rates or phone numbers. Roles are per project: owner = `projects.owner_id`, crew leader = active `project_members` row. |
| Alternatives considered | (a) **Check permissions only in the React app**: rejected, any user can call the API directly. <br>(b) **Send every write through an Edge Function**: secure, but much more code and an extra network hop for simple CRUD. <br>(c) **Separate tables for crew-visible columns**: duplicates data that can drift out of sync. |
| Consequences | **+** Access rules live in one place, are enforced for every client, and are verified by the SQL test script (47 checks, access matrix T-C.1). <br>**+** Revoking a crew leader takes effect on the next request (UC-02 A2). <br>**−** Every new table must enable RLS and get reviewed policies (pull-request checklist item). <br>**−** Developers must call the RPC functions for crew actions instead of plain updates. <br>**−** Stage-status transitions are currently checked only in the client (`ConstructionStage.canTransitionTo`); a crew leader calling `update_stage_progress` directly could skip a state. Accepted as a known limitation unless the team adds a transition check to that RPC. |
