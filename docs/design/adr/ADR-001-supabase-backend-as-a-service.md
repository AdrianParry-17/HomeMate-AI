# ADR-001: Use Supabase as the Backend-as-a-Service

Formalizes PA1 **AD-01** · Date: 2026-11-17 · Deciders: Team T08 · Related: FR-01 – FR-04, NFR-03, NFR-04, R02, R05

| ADR | ADR-001: Use Supabase as the Backend-as-a-Service |
|---|---|
| Status | accepted |
| Context | Five students must build the four Must-have features in the PA5 window (weeks 8–10, 152 planned person-hours) with a 0 VND infrastructure budget (PA1 §4.6). The system needs relational data with totals (budgets, expenses, attendance), accounts with e-mail verification, password reset and invitations, row-level access control for crew leaders (NFR-03), and a server-side place for the Gemini API key (NFR-04). Writing, hosting and securing our own backend server would take a large share of the build window. |
| Decision | Use one Supabase Cloud project (free tier) as the back end: PostgreSQL for data, Supabase Auth for accounts, the generated Data API (PostgREST) for CRUD and RPC calls, and Supabase Edge Functions for the three operations that need secrets. There is no dedicated backend server. We chose Supabase mainly because it is **convenient** (database, auth and API in one managed project and one SDK) and **free** at our usage, while still being a real PostgreSQL database: we keep SQL constraints, triggers, views and Row Level Security, which gives us control close to a self-written backend. |
| Alternatives considered | (a) **Own REST backend** (FastAPI or Node/Express) with PostgreSQL on Render or a VPS, deployed with Docker: full control, but a second codebase to build, host, secure and test. It was in the PA1 draft and removed at the PA1 review. <br>(b) **Firebase** (Firestore, Firebase Auth, Cloud Functions): equally convenient, but a document database fits our relational data and totals poorly, access rules are written in Firebase Security Rules instead of SQL, we get less control over the data model, and deploying Cloud Functions requires the paid Blaze plan. <br>(c) **Next.js API routes on Vercel** with a hosted PostgreSQL: workable, but we would still write and secure server code and integrate an auth provider ourselves. |
| Consequences | **+** No server to operate; sign-up, e-mail verification, password reset and invitations come built in. <br>**+** Schema and access rules are plain SQL and can be tested in SQL (47 checks in `docs/design/data/tests`). <br>**+** 0 VND within the free tier. <br>**−** Tied to Supabase (Auth, PostgREST, Edge Runtime); moving away would mean rewriting auth and data access. <br>**−** Logic is split across TypeScript, SQL and Deno; the team needs SQL and RLS skills (see the "where logic lives" rule in the Architectural Style section). <br>**−** Free-tier limits: the project can be paused after inactivity, the built-in mailer is rate-limited, and Edge Function usage is capped (risk R05). |
